## What are RL environments?

### Technical overview

An RL environment is the sandbox a model acts in, the tools it can call, and the grader that scores
it. It is what turns a task into a training signal.

### White-box vs black-box RL environments

The distinction that matters for this article is not what the task is. It is **who drives the
rollout**.

In a white-box environment the trainer owns the loop: it samples an action, calls `env.step()`, and
every token the policy produced is already in hand. In a black-box environment the agent owns the
loop, inside a sandbox, and the trainer sees nothing but one endpoint being called.

### The capture layer

If the agent owns the loop, the one place you can stand is the wire between the agent and the model.
An OpenAI-spec proxy sits there, and every call the agent makes passes through it.

#### Downsides and limitations

{/* TODO: the honest section. Real ones, all from PR #1036:
    - Capture must happen on the wire. Re-rendering a prompt offline with apply_chat_template drifts
      from what the model actually saw, and a prompt off by one token silently fragments one long
      conversation into several short ones.
    - The endpoint must return token ids and processed logprobs (vLLM with
      --return-tokens-as-token-ids --logprobs-mode processed_logprobs). Without them you get evals,
      not trainable rollouts. SGLang cannot return token ids at all.
    - Hosted on a Space, the proxy must be publicly reachable, because a private Space needs an auth
      header the agent inside the sandbox does not send.
    - reward=None is not zero. It means the verifier never ran; conflating the two makes a dead
      sandbox look like a wrong answer.
    - Validation against ATIF is the only non-self-referential check, and it can come back MISMATCH.
    - Terminology collision worth stating: OpenEnv providers host the env server; Harbor backends
      are the agent-exec sandboxes. --sandbox refers to the latter. */}
