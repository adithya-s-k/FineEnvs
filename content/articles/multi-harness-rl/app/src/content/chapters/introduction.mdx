## Introduction

If you write code with a model, you have probably already run the same weights through two or three
different programs. Claude Code in one terminal, Codex or opencode in another, Cline or Roo Code
inside your editor, maybe Gemini CLI or Crush when you are curious. You may also have noticed
something that is easy to dismiss as a bad day: a model that felt sharp in one of them feels clumsy
in the next. Same weights, same task, different program around it, noticeably different agent.

That intuition is correct, it is measurable, and it is now one of the central problems in
post-training open models.

The program is called an **agent harness**. It owns the loop, decides which tools exist, builds the
context the model sees, parses what comes back, and decides when to stop. From the model's point of
view it is the entire world. And the model you download was almost certainly trained inside exactly
one of them.

### The labs already tell you this, in the fine print

Read the release notes of the newest open-weight models and the same admission keeps surfacing in
different handwriting.

GLM-4.7 promises "significant improvements on complex tasks in mainstream agent frameworks such as
Claude Code, Kilo Code, Cline, and Roo Code" [@zai2025glm47]. Kimi K2 reports Terminal-Bench twice,
25.0 under Terminus and 30.0 inside Moonshot's own framework, as two rows of one table
[@kimi2025k2]. MiniMax M2 names a different harness for almost every benchmark it lists
[@minimax2025m2card]. DeepSeek-V3.2 runs a robustness check across Claude Code and RooCode, then
admits its thinking-mode context management is incompatible with Terminus, so that number had to be
produced somewhere else entirely [@deepseek2025v32].

Sit with that last one. A frontier lab shipped a model that could not run in a major harness,
noticed, and reported the score from a different one.

Which harness a model is good in has become a shipping claim, printed next to the benchmark numbers,
because nobody runs raw weights. They run Claude Code with your weights behind it.

And when a vendor publishes the same benchmark under two scaffolds, the ranking itself can move.
ByteDance's Seed-OSS-36B card has two SWE-Bench Verified rows covering the same models, and between
them the order flips twice [@bytedance2025seedoss]. Part of each gap is test-time compute rather than
the scaffold, since the Agentless row uses best-of-40 sampling. That objection kills the raw point
gaps and leaves the reversals standing: extra sampling can move a score, but it does not explain why
it moves one model past another and a second model the opposite way.

"Model A is better than model B" turns out not to be a scaffold-invariant statement. Anthropic wrote
this down plainly back in 2024: "the performance of an agent on SWE-bench can vary significantly
based on this scaffolding, even when using the same underlying AI model" [@anthropic2024swebench].
What has changed since is the size of the effect, and how much now rides on it.

### How badly it breaks

Not gently, is the answer. The Orchard team trained a software-engineering agent in one harness and
then ran it in others [@peng2026orchard]:

| System | OpenHands | mini-swe-agent | Kimi-CLI (unseen) |
|---|---|---|---|
| **OpenSWE-32B**, single-harness | 62.4 | 54.9 | **3.6** |
| **Orchard-SWE**, multi-harness | 62.1 | 64.3 | **45.0** |

A model that resolves 62.4 percent of SWE-bench Verified in the harness it was trained in resolves
3.6 percent in one it has never seen. That is not a worse score, it is a broken one. A second system
in the same table, Scale-SWE, does not even produce valid tool calls outside its native harness, so
it has no score at all.

If you have ever watched a local model emit a tool name its harness has never heard of, or leak raw
markup into a field that wanted JSON, you have seen the small version of this. The model is not
confused about the task. It is confused about the interface, and the interface is the only thing it
can see.

The KwaiKAT team gives the failure a name, harness scaling, and the sharpest description of it in
the literature [@kwaikat2026katcoder]:

> "In agentic RL, if training relies solely on a single fixed harness, the model often learns not
> 'how to solve the task' but 'how to solve the task under that particular harness's interface
> conventions.'"

They split it into three modes, worth carrying for the rest of this article. **Format overfitting**
anchors the model to one action format, so parse failures spike when the tool protocol changes.
**Context-structure overfitting** makes it depend on one harness's history-concatenation order.
**Control-flow overfitting** leaves it leaning on someone else's reflection timing and stopping
conditions, unable to plan for itself when that scaffolding is gone.

### Frontier labs stopped reporting this and started training for it

The fix is to vary the harness during rollouts, which KwaiKAT describes as domain randomization
applied to the environment. Labs are now paying real money to do it.

poolside's Laguna report has a section titled Multi-harness Training, and its first sentence is this
article's thesis written by someone else first [@poolside2026laguna]:

> "To encourage generalization across diverse agent harnesses, our training data includes
> trajectories from external frameworks such as OpenHands, OpenCode, and Mini-SWE-Agent."

That is 1.3 billion tokens of agentic trajectories from three harnesses that are not theirs, with
each one's native behaviour deliberately preserved, "including custom subagent spawning, context
compaction, planning scaffolds, and reminder systems." Their RL phase then runs through the harness
they ship to customers, so "any change to the deployed harness is also a change the policy is
trained against."

The obvious worry is that spreading training across harnesses buys robustness by giving up peak
performance on the one you actually care about. The only controlled ablation published so far says
the opposite. OpenForgeRL trained one base model on a single harness and on three, and the
three-harness run won even on the single harness's home turf, 48.5 against 46.0, while nearly
tripling Codex [@yu2026openforgerl]. They credit the wider variety of tool calls and control flows
the model sees. Harness diversity behaved like a regularizer, not a tax.

### What is missing

Not the idea, and not the tooling. Microsoft's Agent Lightning takes Qwen3.5-9B from 41.8 to 56.4
percent on SWE-bench Verified using roughly 6,000 training examples and modest compute
[@he2026agentlightning]. That is not a frontier-scale result and it is not meant to be. It is proof
that this work now fits inside what a small team, or one person with a rented node, can actually run.

What is missing is an open one. Every published result that trains across the harness cross-product
comes from a closed or semi-closed lab. Nobody has swept how many harnesses you need, or along which
axes, before the returns flatten out. The abstractions exist, in OpenEnv, in verifiers, in SkyRL, in
Harbor, and the run does not.

That gap is what the rest of this article is for: what a harness actually is, what an RL environment
actually is, how to capture trainable tokens out of an agent you do not control, and then the thing
itself, a small open model trained across many harnesses, evaluated in all of them, with the parts
that did not work left in.
